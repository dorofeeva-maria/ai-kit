# docs — the change explained where the next reader will look

Code shows what the system does; the docs say how to use it, why it is so, and what a person or
an agent must know before touching it. A change without its docs is half-delivered: the next
reader works from a description of a system that no longer exists. Shared terms (task file,
profile, reports): [contract](../../docs/contract.md).

**When:** last — after the review and its fixes, before the PR is declared ready, so the docs
describe the final code. In the `task` pipeline the reviewer then re-checks only your docs diff
and the PR description; its findings come back to you.

## Read first

- Your brief, the task file (Request, Decisions, Plan), and the implementers' reports.
- **The diff itself** against the base branch, per repo (`git diff <base>...HEAD`). Document the
  code as it is, not the plan: where they differ, the code wins and the difference is reported.
- The profile: Git and PRs (description rules), Language (docs language), Never.
- Each repo's `AGENTS.md` / `CLAUDE.md` and how it keeps docs: a `docs/` folder, READMEs per
  package, an ADR folder, a decisions file, a changelog, generated API docs.

## Find what the change touched

For each changed behaviour, ask where a reader would look for it, and search there (grep the
names of changed functions, endpoints, commands, settings, screens, env variables):

| Kind | Typical places |
|---|---|
| User docs | guides, help pages, screenshots, examples, CLI `--help` text |
| Technical docs | architecture and module docs, API reference, data schema, runbooks |
| READMEs | setup, configuration, commands, environment variables |
| Instructions for AI agents | `AGENTS.md`, `CLAUDE.md`, skills, prompts that describe this code |
| Records | ADRs, a decisions file, a changelog, the task file's Decisions |

Agent instructions count as docs: an `AGENTS.md` that names a removed command or an old folder
misleads every agent that reads it.

## Write

- **Update in place**; prefer changing an existing page over adding a new one. Remove what is no
  longer true — do not leave it with a "deprecated" note unless users need the transition.
- **Short and clear, for people and for AI**: lead with what to do or what is true; real names,
  paths and commands; one example where it saves a paragraph. No marketing, no history of how
  the code got here (that goes to records).
- Follow the repo's existing docs style, structure and language.
- **Never document what was not built**: no planned features, no options that do not exist yet.
  Something to come → the task file or a tracker item, not the docs.
- Generated docs are regenerated by their command, never edited by hand.

## Record decisions

Where the repo keeps such records (ADR, a decisions file, a changelog), add each decision of this
change that a later reader would question: what was decided, the reason, the options rejected,
the date. Follow the record's own format and numbering. No such place in the repo → the task
file's `## Decisions` holds them. Decisions that change the system's structure always get a
record — the history survives only where it is written.

## Record new patterns

A change often brings a way of doing things the repo had not written down: a new interaction or
screen pattern (how a field that may meet another person's edit behaves, how one input means
different actions by what is typed — an empty value deletes, for example), a code convention, an
error shape, a test approach. It may be invented in this task, or **taken from another app, repo
or project** — a sibling app's design system, another project's rule or instruction. Either way,
this repo must hold it, so the next person or agent here finds it without knowing where it came
from.

- Read the diff and the task file's Decisions for every such pattern. Ask: would someone building
  the next screen or module here make the same choice without being told? If not, write it down.
- Write it where this repo keeps such rules: its design system's rules or pattern pages, its
  style or conventions guide, its `AGENTS.md` table of rules — following that place's format.
  State the rule, when it applies, one real example from this change, and the reason.
- A pattern taken from elsewhere: write it **in this repo's own words and terms**, and name the
  source (repo and page, or project) in one line. Never only link to the other project: it is not
  read from here, and it may change.
- If it differs from what the source does, say what differs and why.
- No place for such rules in the repo → name the gap in your report, with the file you propose.

## What became outdated elsewhere

Docs you may not or cannot change — another repo, a wiki, a design file, a page outside the
workspace — list in the report: where, what is now wrong, what it should say. Do not edit outside
your scope.

## The PR description

Per the profile's Git and PRs rules. It tells the truth about **the current code** of this PR:

- what the PR does, in two or three lines, and the task key;
- what changed, grouped by area, not by commit;
- how it was checked: by running (commands, what was seen), by reading, not at all;
- what is not done, known limits, what a later PR brings (in a chain of PRs: its place in the
  merge order);
- anything the reviewer or the person merging must do (migration, config, a flag).

Nothing the code does not do; nothing from an earlier draft of the plan. Re-read it against the
final diff before handing over.

## Same PR

Docs go into the same PR as the code they describe, as their own commit(s) in the profile's commit
format. A docs-only follow-up PR is the exception, and only when the brief says so.

## Hand over

A report in the part's folder `tasks/<KEY>/<part>/` and a short reply, conclusion first: the files changed per repo
(one line each), the decisions recorded and where, what became outdated outside your scope, the
PR description (or its path), and what you did not check.
